# D17: distinguish client and server wait times

The owner requested reduced concurrent startup latency within an approximately JPY 5,000 monthly budget. The prior one-session, 15-own-card-read test completed 15/15 requests, with a 10.652-second median and 15.743-second maximum. The slowest sample had 5.755 seconds in the existing server timer; its remaining 9.988 seconds cannot be assigned to the browser, network, or Cloud Run pending time from that report alone.

D17 retains the D16 rollout flags and explicit per-device fallback. It works with both FIX3 and FIX4 backends. The new `P086-CONCURRENT-READ-2` report adds per-request SDK, local ticket check, token, response-header, and body timings. A fixed diagnostic query separates browser resource entries from ordinary app calls; baseline and batch use the same URL so the baseline prepares the same CORS preflight cache. Resource timings are reported as aggregate sample arrays, not falsely correlated to individual requests. No URLs, request IDs, names, credentials, private card contents, or arbitrary server error text are copied.

FIX4 additionally permits Resource Timing only for the existing entry origin and returns numeric `Server-Timing` durations. An older server or unsupported browser produces null/unavailable details, never fabricated zero queue time. Browser `preRequestMs` includes connection/preflight/other browser-side work; `waitResponseMs` includes network and server work. Neither is labeled as pure server queue time. The read-only Cloud Monitoring helper in the private patch can distinguish service-side pending time using built-in metrics.

The private backend patch separately changes concurrency from 4 to 8 while retaining minInstances 1, maxInstances 2, CPU 1, and memory 512 MiB. Response compression becomes asynchronous. Business authorization, request replay prevention, and final live checks remain in place. Publication of this public entry alone does not deploy those server changes; live performance and actual project billing must still be verified after deployment. GAS remains FIX3 and requires no redeployment.
